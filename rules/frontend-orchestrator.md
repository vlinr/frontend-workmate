# 前端流程入口

## 入口说明

- 根级 `SKILL.md` 定义主编排协议
- 本文件是流程入口代理，负责把主协议映射到各阶段规则
- **每个阶段执行完成后，必须显式输出阶段完成结论**，格式为：`[阶段名称] 执行完成。结论：xxx。接下来进入下一阶段：[下一阶段名称]。`
- 阶段名称：初始化、项目扫描、范围分析、执行计划、资料补充、实施研发、内部验证、文档同步、交付续跑。

## 核心链路

1. Stage 0 开始时，若【当前技能目录】存在 `scripts/init-skills.js`，必须先主动执行该脚本，再继续任何后续初始化动作；若本轮未实际执行，则 Stage 0 不得视为完成。脚本用于把技能目录整理成可直接调用的公共技能包；若源目录已不存在或目标技能已存在且非空，则记录为跳过
2. 每个阶段正式执行前，先扫描当前可用技能来源：用户提供的 skills / 文档、项目技能 `fw-project-develop`、项目内已归档 skill、其他可复用公共技能包
3. 若已命中合适技能，优先调用并按其约束执行；不要先裸跑阶段再回头补技能
4. 对齐 `templates/intake/request-brief.md`
5. Stage 0 仅负责环境初始化、文件接收、状态初始化与进入 Stage 1 判定，不负责生成实现问题清单；在进入 Stage 1 前，不得主动追问实现范围、接口字段、校验规则、交互细节或还原标准
6. Stage 0 完成时，用户侧默认只输出简短正文，例如"正在初始化..."或"初始化已完成，继续处理下一环节。"；不得把 `current_stage`、`entry_conditions`、`completion_conditions` 等内部字段直接摊给用户
7. 新会话首轮默认只允许一个阻塞问题；但如果已经识别到唯一现有前端项目，则直接进入 Stage 1 扫描，不额外发问"是否继续现有项目"
8. Stage 1 首轮项目基线判定规则：
   - 唯一现有前端项目：直接锁定并进入扫描/生成项目 skill
   - 多个前端项目：首轮唯一允许主动发问的问题是"本次基于哪个前端项目继续"
   - 未识别到前端项目：首轮唯一允许主动发问的问题是"是否需要初始化前端项目"
9. 仅在用户进入"初始化"分支后，下一轮再询问初始化组合，并按"底层框架 + 语言框架 + 语言 + UI 库"表达；不得把"唯一现有项目"错误地拉回初始化分支
10. **Stage 1 初始化项目分支流程**：
    - 询问初始化组合 → **等待用户答复**
    - 执行初始化命令 → **扫描新项目结构** → **生成项目技能 fw-project-develop**
    - 输出项目技能摘要 → **等待用户确认**
    - 用户确认 → **进入 Stage 2**
    - 注意：Stage 0 的"初始化"只负责执行 init-skills.js，不生成项目技能
11. 参考 `rules/project-scan-profile.md`
12. Stage 1 的完成条件是"已生成或刷新项目技能 `fw-project-develop`，或已命中稳定可复用项目技能"
13. Stage 2、Stage 5、Stage 6 开始前，**必须先调用项目技能 `fw-project-develop`**，获取项目约束
14. Stage 1 完成后，向用户汇报项目基线与项目技能结论，并确认结论是否正确；用户未确认前，不得进入 Stage 2
15. 参考 `rules/frontend-change-scope.md`
16. Stage 2 形成任务类型、修改范围、风险和技能路线后，只需要让用户确认"我的理解是否正确"；用户补充后要先合并分析再继续确认，未确认前不得进入 Stage 3 或 Stage 4
17. 若已安装或识别到自定义/私有 UI 库，Stage 2 还必须先判断是否需要向用户询问组件库文档、skills 或关键组件规则；在得到"提供 / 不提供 / 跳过"的明确答复前，不得进入研发
18. 若任务较长或较复杂，执行 `task-plan-checkpoint`
19. Stage 3 仅在执行计划本身需要用户核对拆分、优先级或风险时才停住；否则可直接进入 Stage 4（执行前确认资料）
20. Stage 4 按任务类型确认接口、权限、设计、联调等前置资料：`feature` 默认确认，`bug` 仅在涉及外部依赖时确认，`refactor` 默认可跳过
21. 若 Stage 2 已确认任务类型和技能路线，Stage 5 必须根据实际条件调用对应技能：
    - `bug` 任务 → 必须调用 `systematic-debugging`
    - React 技术栈（项目技能中标记） → 必须调用 `react-best-practices`（仅适用于 React）
    - React 技术栈且涉及组件开发 → 必须调用 `react-components`（仅适用于 React）
    - 复杂类型问题 → 必须调用 `typescript-advanced-types`
    - 禁止以"Stage 2 没有指定"为由跳过技能调用
    - 禁止在非 React 技术栈下调用 React 技能
22. Stage 4 在用户已明确"提供 / 不提供 / 跳过"资料后，直接进入 Stage 5 正式实现；不再额外询问是否继续
23. 参考 `rules/frontend-implementation.md`
24. Stage 5 只有在代码实现完成且不存在未解决的运行/lint/type/build/test 阻塞时，才允许自动进入 Stage 6；若存在环境问题，必须先停留在 Stage 5 并向用户输出修复建议
25. 参考 `rules/frontend-verification.md`，并根据代码改动调用验证技能：
    - 改动涉及页面/组件/表单/键盘交互/焦点流 → 必须调用 `accessibility`
    - 改动涉及布局/样式/间距/UI 一致性 → 必须调用 `web-design-guidelines`
    - 禁止以"时间紧迫"为由跳过技能调用
26. Stage 6 输出验证结果后，必须等待用户确认是否继续；若验证失败、环境阻塞或用户要求调整，回到 Stage 5；只有用户确认后才进入 Stage 7
27. 参考 `rules/directory-doc-sync.md`，并按实际改动目录逐个生成或更新目录说明文档
28. Stage 7 完成后直接进入 Stage 8，不再额外等待用户确认
29. 汇总交付结果，并在长任务模式下回写任务状态

## 提问门禁

- 只要当前阶段缺的是用户输入，就必须先判断交互类型：`provide`、`confirm`、`choose`、`approve`、`correct`
- 向用户发起提问时，提示语必须匹配当前意图：缺资料用"请提供"，校对结论用"请确认"，分支决策用"你可以回复 1/2/3、A/B/C，或直接告诉我你的选择/想法"，风险接受用"若接受请回复继续"，纠偏用"如有问题请直接指出"
- 向用户发起提问前，还要判断提问方式：
  - 需要用户补文档、skills、路径、截图说明、接口说明、组件约束等内容时，使用普通文本回复引导，不使用选择器
  - 只有极少数宿主环境强制要求的有限分支决策，才使用选择式交互；默认仍使用文本列项，允许用户回复数字、字母、短标签，或直接描述自己的想法
- Stage 1 首轮提问仅在"多项目歧义"或"无前端项目需初始化"时触发；唯一现有前端项目不为形式确认而额外发问
- 新会话首轮若仍停留在 Stage 1，不得混入 Stage 0 缺失细节或 Stage 2 范围问题
- Stage 1 与初始化分支默认采用"直接询问用户"的文本方式，不默认弹出可点击选项
- 默认不是每个 Stage 都确认；只有当前结论需要用户确认、正式研发前仍缺少必要资料，或验证结果需要用户明确放行时才停住
- "明确同意进入下一步"的最小判定标准：用户回复必须是纯放行语句，语义上不包含任何新增需求、修正、限制、路径、页面、文件、接口、交互、校验、样式、文案、行为或实现方向信息
- 若同一条用户回复同时包含"继续"与任何新信息，优先按"补充/修正诉求"处理，仍停留在当前阶段
- 若用户在阶段确认点补充、修正或扩展诉求，必须停留在当前阶段，先合并诉求并更新当前阶段结论；不得把这类回复视为"同意进入下一步"
- 合并诉求后的提示语必须根据用户回复类型动态生成：
  - 用户提供资料：`我已接收并吸收你提供的资料。以上是当前阶段的最新结论；如果还有偏差或补充，你可以直接告诉我。`
  - 用户补充/修正诉求：`我已合并你刚补充的诉求。以上是当前阶段的最新结论；如果还有偏差或补充，你可以直接告诉我。`
  - 用户明确不提供/跳过：`我已记录你暂不提供该资料。以上是当前阶段的最新结论；如果还有偏差或补充，你可以直接告诉我。`
  - 用户仅确认：`我已记录你的确认。` 后接当前阶段需要的下一步动作；不得误写成"已合并资料"
- 仅显式确认点才需要同时明确两件事：用户补充诉求时留在哪一步，用户否定结果时回退到哪一步
- `Stage 0` 是临时调试准备步骤，只有停留与继续，没有额外回退目标
- 用户侧默认不展示阶段内部字段列表；只展示当前步骤的简短摘要、关键结论，以及"可继续/可补充/可修改"的提示
- 确认提示不能只写"回复继续"；必须同时允许用户补充或修改当前步骤结论
- **显式确认点的标准提示语**（必须使用）：
  > "如果您还有其他需要修改的，请告诉我；当然如果没有其他修改，您可以直接回复'继续'，我将进入下一步。"
- 此提示语适用于：项目扫描确认、范围分析确认、内部验证确认
- 禁止省略"如果您还有其他需要修改的，请告诉我"部分
- 禁止在最后一步（交付续跑完成后）附加提示语
- 提问或说明一旦发出，当前回复必须结束并等待用户输入；不得在同一回复中继续分析、调用下游技能、修改文件、执行命令或初始化项目
- 命令 approval、工具确认、终端交互提示，不得视为用户对业务问题的明确答复

## 阶段切换规则

- 每次准备进入新阶段前，必须先显式写清：
  - `current_stage`
  - `current_stage_status`
  - `next_stage`
  - `stage_block_reason`
- 每个阶段结束前，还必须显式给出该阶段的最小过站产物，不允许只在内部完成分析后静默切换阶段
- 若当前阶段仍未完成，不要只写"继续下一步"，而要明确保持在当前阶段。
- 只有在当前阶段状态为 `completed` 时，才能切换到下一阶段。
- 若当前阶段状态为 `waiting_user` 或 `blocked`，必须停止在当前阶段，不能因为项目已创建、依赖已安装或代码可编辑就自动前进。

## 失败回退

- 若项目技能缺失、命名混乱或无法匹配，回到项目扫描阶段并生成规范化项目技能。
- 若 Stage 1 只是完成了初始化或依赖安装，但尚未生成项目技能，仍视为停留在 Stage 1。
- 若阶段推进依赖用户输入但用户尚未明确答复，必须停留在当前阶段等待，不能自行假设继续执行。
- 若当前回合已经向用户发起提问，则当前回合不得继续推进到下一个 Stage。
- 若 Stage 2 无法给出稳定的任务范围与技能路线，不得进入研发，需回到范围分析。
- 若自定义/私有 UI 库的文档、skills 或关键组件规则尚未形成"提供 / 不提供 / 跳过"的明确结论，不得进入研发，需停留在 Stage 2。
- 若某个关键技能不可用、产出不稳定或与项目约束冲突，先回到 Stage 2 重新规划，再决定是否改用 `find-skills` 或人工降级方案。
- 若验证阶段关键门禁失败，必须回到研发阶段，不能跳过进入文档或交付。

## 规则

- 把本文件视为流程入口代理，不视为独立总规范
- 阶段门禁、循环回路、回退逻辑全部以根级 `SKILL.md` 为准
- 仅使用仓库内相对路径
- 不存在的可选逻辑统一标记为 `not_applicable`
