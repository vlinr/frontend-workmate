# ⚠️ 核心强制规则（必须遵守）

## 1. 单一阶段输出原则（最重要）

**AI 每次输出必须只包含当前阶段的内容，禁止幻想未来阶段**：

| 规则 | 说明 |
| --- | --- |
| **禁止多阶段输出** | 输出只能包含当前阶段的内容，不得包含"接下来要做什么"、"后续计划"等 |
| **禁止自创任务列表** | 必须使用本文件的"任务状态列表"，不得自行创建任务计划 |
| **禁止幻想未来** | 不得在当前阶段输出未来阶段的计划或预期结果 |
| **禁止跨阶段承诺** | 不得承诺"完成后会xxx"，必须等待实际执行后再输出 |

**正确示例**（stage0）：
```
[初始化] 任务ID: task_a1b2c3d4
正在初始化...
[初始化] 执行完成。接下来进入下一阶段：[项目扫描]。
```

**错误示例**（stage0）：
```
任务计划：
1. 创建项目
2. 安装依赖
3. 实现页面
4. 验证优化 ← 禁止！这是幻想未来阶段
```

## 2. 任务ID携带原则（强制）

**AI 每次输出必须携带当前任务ID**：

```
输出格式：
[阶段名称] 任务ID: {当前任务ID}
{当前阶段的输出内容}
```

| 场景 | 任务ID位置 |
| --- | --- |
| 进入任何阶段 | 第一行输出：`[阶段名称] 任务ID: task_xxxxxxxx` |
| 等待用户确认 | 状态块中包含任务ID |
| 用户提出修改 | 更新状态块时携带任务ID |
| 任务完成 | 输出：`任务ID: task_xxxxxxxx 已完成` |

**禁止事项**：
- 禁止输出时不携带任务ID
- 禁止脱离任务上下文执行其他操作
- 禁止忘记当前任务ID

## 3. 阶段确认闭环原则（强制）

**每个阶段必须等待用户确认后再进入下一阶段**：

| 阶段结束条件 | 必须执行的动作 |
| --- | --- |
| 阶段有产物输出 | 输出摘要 + 等待用户确认的提示语 |
| 用户确认"继续" | 更新状态 → 进入下一阶段 |
| 用户提出修改 | 停留当前阶段 → 合并反馈 → 再次输出等待确认 |
| 用户未回复 | 结束当前输出 → 等待用户回复 |

**禁止事项**：
- 禁止未经用户确认就进入下一阶段
- 禁止连续输出多个阶段的内容
- 禁止在等待确认时输出其他内容

# 任务ID规则

## 任务ID生成

**初始化时（stage0）生成任务ID**：
- 格式：`task_` + 8位随机字符（如 `task_a1b2c3d4`）
- 目的：唯一标识一个任务，便于状态追踪和更新

## 任务ID使用

**AI 必须在以下场景携带任务ID**：
1. 更新任务状态时：根据任务ID定位对应的状态块
2. 输出给用户时：在关键节点输出任务ID，便于用户引用
3. 任务切换时：用户可通过任务ID指定回到某个任务

## 任务ID查找规则

**更新状态时的查找逻辑**：
```
1. 从上下文获取当前任务ID
2. 在任务列表中查找该任务ID对应的状态块
3. 若找到 → 更新该状态块
4. 若未找到 → 新增一个任务状态块（新任务）
```

## 任务回收规则

**任务完成时的回收逻辑**：
```
1. 任务进入 stage8 且用户确认无修改
2. 状态标记为 completed
3. 用户可选择：
   - 继续保留（便于回顾）
   - 回收清理（标记为 recycled，移除详情）
4. 任务列表最多保留 5 个已完成任务的历史
5. 超过 5 个时，自动回收最早的任务
```

# 意图判断规则（stage1 专用）

**当未识别到前端项目时，收到用户回复后必须先提取内容**：

## 内容提取规则

**从用户回复中提取两类信息**：

| 信息类型 | 提取规则 | 处理方式 |
| --- | --- | --- |
| **初始化信息** | 技术栈、框架、语言、UI库等 | 当前阶段（stage1）立即处理 |
| **研发需求信息** | 功能需求、页面描述、bug描述等 | 记录到任务上下文，等 stage2 处理 |

**提取示例**：
```
用户回复："创建项目：React + TypeScript + Ant Design，要有登录页面、用户管理"

提取结果：
- 初始化信息：React + TypeScript + Ant Design → 立即初始化项目
- 研发需求信息：登录页面、用户管理 → 记录到 pending_requirements
```

---

## 意图类型判断

| 提取结果 | 意图类型 | 执行路径 |
| --- | --- | --- |
| 提取到技术栈（React/Vue/Angular） | **初始化意图** | 执行项目初始化 |
| 用户回复"退出"或"结束" | **终止意图** | 终止流程 |
| 空回复或"跳过" | **默认方案意图** | 采用默认技术栈（React + TypeScript + Ant Design） |
| 用户提供现有项目路径 | **路径切换意图** | 切换路径重新扫描 |
| 仅提取到研发需求，无技术栈 | **需要补充技术栈** | 询问补充 |

---

## 研发需求记录规则

**若用户提供了研发需求信息，必须记录到任务上下文**：

```
记录位置：pending_requirements
记录时机：提取用户回复后立即记录
处理时机：stage2（范围分析）阶段处理
```

# 各阶段职责边界（防止内容混淆）

**核心原则**：用户可以提供任何内容，AI只提取当前阶段需要的信息，其他信息记录到任务上下文。

---

## 职责边界表

| 阶段 | 负责的内容 | 不负责的内容（记录到上下文） |
| --- | --- | --- |
| stage0 | 初始化、任务ID生成、诉求记录 | 项目分析、范围分析、实现方案 |
| stage1 | 项目扫描、项目技能生成、技术栈识别 | 研发需求、功能描述、bug描述 |
| stage2 | 范围分析、任务类型判断、改动文件识别 | 具体实现方案、代码修改、技能调用 |
| stage3 | 执行计划、任务拆分 | 研发实施、具体代码修改 |
| stage4 | 资料补充（按任务类型判断是否需要） | 研发实施、代码修改 |
| stage5 | 代码修改、研发实施、技能调用 | 验证执行、文档更新 |
| stage6 | 验证执行（lint/type/build/test） | 代码修改（回到 stage5） |
| stage7 | 文档同步、项目技能更新 | 验证、代码修改 |
| stage8 | 交付确认、任务回收、续跑切换 | 研发实施（回到 stage5） |

---

## 内容处理流程

**用户可以提供任何内容，AI按以下流程处理**：

```
用户提供内容 → 内容提取 → 判断属于哪个阶段 → 
  若属于当前阶段 → 立即处理
  若不属于当前阶段 → 记录到任务上下文 → 后续阶段处理
```

```
- 技术栈 → 本阶段处理（初始化项目）
- 研发需求 → 记录到任务上下文（stage2 处理）
```

```
处理：分析范围 + 记录实现细节 → 进入 stage5
```

---

## 内容处理原则（重要）

1. **用户可以提供任何内容**：不限制用户输入
2. **AI只提取当前阶段需要的信息**：不处理不属于当前阶段的内容
3. **其他信息记录到任务上下文**：等后续阶段处理
4. **不拒绝用户内容**：只分阶段处理，不告知"不要提供"

---

## 记录到任务上下文的方式

```
任务上下文变量：
- pending_requirements：研发需求信息
- pending_technology_stack：技术栈信息（等 stage1 处理）
- pending_implementation_details：实现细节（等 stage5 处理）
- pending_documentation：文档补充（等 stage7 处理）
```

---

## 禁止事项

- ❌ 禁止告知用户"不要提供其他内容"
- ❌ 禁止拒绝用户内容
- ❌ 禁止在本阶段处理不属于本阶段的内容
- ✅ 只提取当前阶段需要的信息，其他记录到上下文

| --- | --- | --- | --- |
| stage0 | 自动进入 stage1 | 无 | 无 |
| stage1 | 进入 stage2 | 保持 stage1 → 循环 | stage1 → stage1 |
| stage2 | 进入 stage3/stage4 | 保持 stage2 → 循环 | stage2 → stage2 |
| stage3 | 自动进入 stage4 | 回到 stage2 | 无 |
| stage4 | 自动进入 stage5 | 无（可跳过） | 无 |
| stage5 | 自动进入 stage6 | 在 stage8 统一处理 | stage5 → stage6 → stage7 → stage8 |
| stage6 | 自动进入 stage7 | 不暂停 | stage5 → stage6 → stage7 → stage8 |
| stage7 | 自动进入 stage8 | 不暂停 | stage5 → stage6 → stage7 → stage8 |
| stage8 | 任务完成/回收 | 切换到 stage5 → 循环 | stage5 → stage6 → stage7 → stage8 → 循环 |

# 研发循环流程（stage5 → stage8）

```
用户确认范围分析后：
├─ 进入 stage5（实施研发）← 携带任务ID
├─ 自动进入 stage6（内部验证）← 不暂停，携带任务ID
├─ 自动进入 stage7（文档同步）← 不暂停，携带任务ID
├─ 进入 stage8（交付续跑）← 携带任务ID
├─ 输出交付结果，等待用户确认
├─ 用户提出修改：
│   ├─ 立即切换到 stage5（携带任务ID）
│   ├─ 执行修复 → stage6 → stage7 → stage8
│   ├─ 再次等待确认 → 循环
├─ 用户确认无修改：
│   ├─ 标记任务为 completed
│   ├─ 用户可选择回收或保留历史
│   ├─ 若发起新任务 → 生成新任务ID
```

# 最重要规则

**AI 收到用户输入后，必须按以下顺序执行**：

### 第一步：检查当前阶段状态（必须首先执行）

```
1. 读取状态文件，获取当前任务的状态块
2. 检查当前阶段（stage）和状态（status）
3. 根据当前阶段决定如何处理用户输入
```

### 第二步：根据当前阶段处理用户输入

| 当前阶段 | 状态 | 用户输入类型 | 正确处理方式 |
| --- | --- | --- | --- |
| stage8 | waiting_user | 修改内容/bug描述 | **必须先更新状态为 stage5** → 执行修复循环 |
| stage8 | waiting_user | "确认"/"继续" | 标记任务完成 → 进入回收阶段 |
| stage8 | waiting_user | "进入步骤X" | 更新状态为指定阶段 → 执行对应阶段动作 |
| stage1-7 | waiting_user | 任何内容 | 执行当前阶段的用户回复处理逻辑 |
| completed | completed | 新需求 | **生成新任务ID** → 从 stage0 开始 |

### 第三步：执行阶段动作（不得跳过状态更新）

**如果当前阶段是 stage8 且用户提出修改**：
1. **必须先使用 edit 工具更新状态文件**
2. 更新状态为：`**阶段**: stage5`、`**状态**: in_progress`
3. 然后执行 `stages/implementation.md` 的修复流程
4. **禁止直接修改代码而不更新状态**

**禁止事项**：
- 禁止跳过状态检查直接处理用户内容
- 禁止不更新状态文件就执行修复
- 禁止跳到其他阶段或其他任务的状态
