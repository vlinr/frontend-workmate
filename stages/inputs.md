# Stage 4：执行前确认资料

## 目标

- 在正式研发实施前，按任务类型收集必要的前置资料。
- 确保研发阶段有足够的输入信息，降低因资料缺失导致的返工风险。

## 输入

- 任务类型（bug / feature / refactor）
- 技能路线
- 项目技能 `fw-project-develop`（必须调用）

## 资料确认策略（按任务类型）

| 任务类型 | 默认确认项 | 仅按需确认项 | 默认跳过项 |
| --- | --- | --- | --- |
| `feature` | 接口文档、权限说明、设计稿、联调地址、三方库文档 | - | - |
| `bug` | - | 仅当范围分析表明问题涉及接口、联调、权限、设计或三方库时确认 | 其他 |
| `refactor` | - | - | 全部（除非范围分析识别出新增外部依赖） |

## 执行动作

1. **先调用项目技能 `fw-project-develop`**，确认项目已有的接口、权限、设计规范。
2. 根据任务类型，判断需要确认的资料清单：
   - `feature`：主动向用户确认接口、权限、设计、联调、三方库资料
   - `bug`：仅在范围分析表明问题涉及接口、联调、权限、设计或三方库时询问
   - `refactor`：默认跳过；若范围分析识别出新增外部依赖，才询问对应资料
3. 若需要用户补充资料，向用户发起 `provide` 类型提问，并明确告诉用户可以：
   - 直接提供资料内容
   - 回复"不提供"或"跳过"
4. 若用户明确"提供 / 不提供 / 跳过"，则记录对应状态并继续；不把"不提供/跳过"当作硬阻塞，但需记录风险。
5. 若用户状态仍为 `pending`，则停留在本阶段等待，不得进入 Stage 5。
6. 本阶段完成后，自动进入 Stage 5 正式实施；不再额外询问是否继续。

## 输出

- 必须至少形成一个最小 Stage 4 过站产物：
  - `current_stage = stage4`
  - `current_stage_status`
  - `stage_goal`
  - `entry_conditions`
  - `completion_conditions`
  - `next_stage = stage5`
  - `stage_block_reason`
  - 资料确认结果清单（每项资料的状态：`provided | not_provided | skipped | pending | not_applicable`）

## 回退条件

- 若后续研发阶段发现资料不足导致无法继续，可回退本阶段补充询问。
- 若用户主动补充新资料，可重新进入本阶段合并。
