# Stage 5：实施研发

## 目标

- 根据任务类型与项目规则执行实际代码修改。

## 第一步：更新状态文件

**进入本阶段后，必须立即执行以下编辑操作**：

### 进入本阶段时编辑

使用 edit 工具，将 `<!-- CURRENT_STATUS_START -->` 到 `<!-- CURRENT_STATUS_END -->` 之间的内容替换为：

```
**正在执行**: 实施研发
**阶段**: stage5
**状态**: in_progress
**下一步**: 执行代码修改，完成后自动进入 stage6
**用户提出修改时**: 在 stage8 统一处理（循环）
**循环路径**: stage5 → stage6 → stage7 → stage8 → 循环
```

### 阶段完成后再次编辑

**完成后直接进入 stage6**（不暂停等待用户确认）：

```
**正在执行**: 内部验证
**阶段**: stage6
**状态**: in_progress
**下一步**: 执行功能验证、lint/type/build/test，完成后自动进入 stage7
**用户提出修改时**: 在 stage8 统一处理
**循环路径**: stage5 → stage6 → stage7 → stage8 → 循环
```

### 禁止事项

- 禁止不读取配置文件就猜测路径
- **禁止在 stage5 暂停等待用户确认**（自动执行到 stage8）

## 技能建议调用规则

**本阶段开始时，必须先扫描技能列表是否有可用技能，然后根据实际条件建议调用以下技能**：

### 扫描流程

1. **扫描技能列表**：检查【技能目录】中是否存在以下技能
2. **判断触发条件**：根据任务类型、技术栈、改动类型判断是否满足调用条件
3. **建议使用技能**：满足条件时建议调用对应技能，并在调用前明确说明调用原因

### 建议调用清单

| 触发条件 | 建议调用的技能 | 说明 |
| --- | --- | --- |
| 项目技能存在（【技能目录】中存在 `fw-project-develop`） | `fw-project-develop` | 建议先调用，获取项目结构、技术栈、路由、权限、构建规则等约束 |
| 任务类型为 `bug` | `systematic-debugging` | bug 任务建议先调用系统化调试技能，找到根因后再修复 |
| 技术栈为 React（项目技能中标记） | `react-best-practices` | **仅适用于 React 技术栈**，React 项目实现建议遵循 React 最佳实践 |
| 技术栈为 React 且涉及组件开发或修改 | `react-components` | **仅适用于 React 技术栈**，创建或修改组件时建议遵循组件规范 |
| 涉及复杂类型约束或类型问题 | `typescript-advanced-types` | 类型推导、泛型、条件类型等复杂场景建议调用 |
| 缺少关键技能 | `find-skills` | 发现缺失技能时建议输出安装建议 |
**项目技能说明**：
- `fw-project-develop` 是项目技能，包含项目结构、技术栈、路由、权限、状态管理、构建规则等关键信息
- **建议调用**：本阶段开始时建议先调用项目技能，理解项目约束后再开始实现
- 调用目的：让 AI 理解项目约束，避免违背项目已有规则
### 技术栈说明

- `react-best-practices`、`react-components` **仅适用于 React 技术栈**（项目技能中标记）
- 其他技术栈（Vue、Angular、Svelte 等）目前暂无对应技能
- 技术栈判断依据：调用 `fw-project-develop` 后获取的技术栈字段

### 禁止事项

- 禁止在非 React 技术栈下调用 React 技能
- 禁止在不满足触发条件时强行调用（避免过度调用）
- 禁止以"Stage 2 没有指定"为由跳过技能调用

## 分流规则

- `bug`
   - 建议先调用 `systematic-debugging` 找到根因
   - 若涉及复杂类型问题，建议辅以 `typescript-advanced-types`
- `feature`
   - 参考 `rules/frontend-implementation.md` 执行实现流程
   - 若技术栈为 React（项目技能中标记），建议调用 `react-best-practices`（仅适用于 React）
   - 若技术栈为 React 且涉及组件开发，建议调用 `react-components`（仅适用于 React）
- `refactor`
   - 参考 `rules/frontend-implementation.md` 执行实现流程
   - 默认先保持行为不变
   - 先拆影响范围，再分批实施
   - 若技术栈为 React，同样建议遵循 React 技能调用规则

## 通用动作

1. **开始正式实现前，先扫描技能列表**：
   - 检查【技能目录】中是否存在项目技能 `fw-project-develop`
   - 若存在，建议先调用获取项目约束
   - 调用后获取的约束作为实现参考，避免违背项目已有规则
2. **根据本阶段"技能建议调用规则"判断是否需要调用技能**：
   - 满足条件时建议调用，并在调用前说明原因
   - 不满足条件时不强行调用
3. 对项目技能中标记为 `not_applicable` 的能力，不做虚构实现。
4. 若现场发现新阻塞、环境问题、依赖问题或技能路线缺口，再回写更新，不得假装研发已完成。
5. 若已启用长任务机制（Stage 3），则实施过程中持续回写步骤状态。
6. **代码改动完成后，必须立即衔接 Stage 6 做内部验证**：
   - **禁止**在 Stage 5 完成后询问"功能是否正确"或"是否进入验证"
   - **禁止**输出"请确认功能实现是否满足需求"
   - 直接进入 Stage 6，执行验证后再等待用户确认
7. 若环境问题导致无法执行验证（如 lint/type/build/test 命令不可运行），则输出明确的环境修复建议并保持在 Stage 5，不得进入 Stage 6。

## 输出

- 代码修改
- 配置修改
- 必要的任务状态更新
- 若存在环境问题导致 lint/type/build/test 无法在当前环境完成，则输出明确的修复建议并保持在 Stage 5，不得把该结果当成可进入 Stage 6/7 的完成态

## 回退条件

- 若内部验证失败，回退本阶段继续修复。
- 若运行、lint、type、build 或测试因当前环境问题无法通过，停留在本阶段，先向用户说明修复环境所需动作；环境修复后继续 Stage 5，而不是进入 Stage 6 或 Stage 7。
