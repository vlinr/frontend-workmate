# Stage 2：分析需求与范围

## ⚠️ 强制规则（必须遵守）

### 1. 单一阶段输出原则

**本阶段输出只能包含范围分析内容，禁止幻想未来阶段**：

| 禁止内容 | 说明 |
| --- | --- |
| "实现方案" | 禁止输出实现阶段的内容 |
| "具体修复步骤" | 禁止输出具体实现步骤 |
| 任务分解列表 | 禁止自创任务列表 |

### 2. 任务ID携带原则

**本阶段必须携带任务ID**：
- 第一行输出：`[范围分析] 任务ID: task_xxxxxxxx`
- 状态文件更新必须携带任务ID

### 3. 必须等待用户确认 ⚠️ 强制规则

**⚠️ 重要：范围分析完成后，必须等待用户确认才能进入下一阶段**

范围分析完成后：
- 输出分析结论摘要
- 输出确认提示语
- **结束当前回复**
- **等待用户回复"继续"或提出修改**

**禁止事项**：
- ❌ 禁止输出摘要后直接进入下一阶段
- ❌ 禁止跳过用户确认环节

---

## 目标

- 把项目知识转为本次任务的明确修改范围。
- 始终围绕 Stage 0 建立的最初需求锚点进行范围分析；阶段内新增约束只能细化实现边界，不能替换最初需求。

## 内容处理规则（重要）

**本阶段职责边界**：

| 属于本阶段的内容 | 不属于本阶段的内容（记录到上下文） |
| --- | --- | --- |
| 范围分析、改动文件识别 | 具体实现方案、代码修改 |
| 任务类型判断（bug/feature/refactor） | 具体修复方案、具体功能实现 |
| 长任务判断 | 执行计划细节 |
| 技能路线规划 | 实际技能调用 |

**用户可以提供任何内容，本阶段只处理属于范围分析的内容**：

```
用户可能提供的内容示例：
- "登录页面验证失败，需要检查表单校验逻辑"
- "用户管理要加权限控制，要改5个文件"
- "首页优化要改 webpack 配置"

处理方式：
- 属于范围分析的信息 → 本阶段处理
- 属于实现方案的信息 → 记录到任务上下文，等 stage5 处理
- 不拒绝用户内容，只分阶段处理
```

## 执行流程

**进入本阶段后，按以下顺序执行**：

---

### 步骤 1：更新状态文件

**使用 edit 工具更新状态文件**：

根据当前任务ID（从上下文获取 `current_task_id`）找到对应的状态块：
- 查找 `<!-- TASK_{任务ID大写}_START -->` 到 `<!-- TASK_{任务ID大写}_END -->` 之间的内容
- 替换该状态块内容为：

```
**任务ID**: {当前任务ID}
**正在执行**: 范围分析
**阶段**: stage2
**状态**: in_progress
**下一步**: 执行范围分析，判断任务类型和是否是长任务
**用户提出修改时**: 状态保持 stage2 → 合并用户反馈 → 更新分析结论 → 再次输出
**循环路径**: stage2 → stage2 → 循环直到用户回复"继续"
```

---

### 步骤 2：前置检查与技能加载

**⚠️ 重要：以下检查需要按顺序执行，每个检查点可能需要加载技能**

---

#### 检查项目技能状态

执行以下动作：

1. 加载技能 `fw-project-develop`（使用 skill 工具，不是读取文件）
2. 从技能中获取项目结构和技术栈信息
3. 若项目技能状态为"待生成"，先执行 Stage 1 项目扫描填充项目技能内容

---

#### 读取需求输入

执行以下动作：

1. 读取 `request-brief` 中的"用户原始描述""最初需求锚点"与截图/附件摘要
2. 只要这些字段非空，需把它们视为当前任务主目标输入
3. 只有当"用户原始描述""最初需求锚点""截图/附件摘要"同时为空、且当前任务目标确实无法判定时，才允许向用户追问"这次要做什么"

---

#### 检查代码改动目录说明文档

**⚠️ 重要：此步骤需判断是否需要加载 fw-code-analysis-doc 技能**

执行以下动作：

1. 根据用户输入确定【代码改动目录】（新增/修改的文件所在目录）

2. 检查该目录是否已有说明文档（README.md / AGENTS.md）

3. **判断是否需要加载 fw-code-analysis-doc**：

   **需要加载的条件（满足任一即可）**：

   | 条件 | 具体判断 |
   | --- | --- |
   | 缺少说明文档 | 目录下无 README.md 或 AGENTS.md |
   | 说明文档内容陈旧 | 文档最后更新时间 > 3个月，或内容与当前代码不符 |
   | 实现关系复杂 | 目录下文件数 > 5，或存在多层嵌套结构 |
   | AI 无法自行分析 | 代码逻辑复杂、依赖关系不清晰 |
   | 涉及核心模块 | 目录是项目的核心业务模块（如 pages/、components/） |

4. 若满足上述条件：
   - 加载技能 `fw-code-analysis-doc` 分析代码结构并获取分析指导
   - 根据技能指导分析目录结构

5. 若不满足条件：
   - 直接读取现有说明文档了解目录结构

---

### 步骤 3：核心分析动作（按顺序执行）

**结合项目技能与【代码改动目录】现有说明文档，按以下顺序分析**：

#### 3.1 UI 框架分析
- 重点分析项目当前使用的 UI 框架，并区分通用框架与自研框架
- 若是通用 UI 框架，明确记录框架名、版本、主要组件入口与替代边界
- 若是自研 UI 框架，先确认 Stage 1 是否已命中对应框架 skill
  - 若没有，则回到 Stage 1 先输出提示语询问用户是否提供框架文档或框架 skills
  - 若用户尚未明确回答（`pending`），则停留在本阶段等待，不得继续范围分析
  - 若用户提供框架文档，则基于文档生成并归档到【技能目录】下的 UI 框架 skill
  - 若用户提供框架 skills，则直接存放于【技能目录】并优先复用
  - 只有在用户明确表示不提供框架文档 / skills（`not_provided`）后，且源码中存在可分析的自研 UI 框架时，才能基于源码分析生成对应 skill
  - 若源码也不足以支撑稳定技能，则标记 `not_applicable` 并继续

#### 3.2 参考规则执行分析
- 参考 `../rules/frontend-change-scope.md` 执行范围分析流程

#### 3.3 标记任务类型
- `需求`（feature）：新增功能、新页面、新组件等
- `bug`：问题修复、异常处理等
- `重构`：结构调整、代码优化但不改变行为等
- `优化`：性能优化、体验优化、代码质量提升等
- 输出时明确标注任务类型

#### 3.4 确定修改范围
- **改动文件数**：预估需要修改的文件数量
- **改动文件位置列表**：列出预估需要修改的文件路径
- **受影响模块**：哪些模块会受到影响
- **接口契约**：涉及的接口或数据结构变化
- **风险点**：可能存在的风险
- **回归范围**：需要回归验证的范围

#### 3.5 规划技能调用路线

**⚠️ 重要：以下技能在本阶段（Stage 5 实施研发时）会被调用**

| 任务类型/条件 | 调用的技能 | 用途 |
| --- | --- | --- |
| `bug` 任务 | `fw-systematic-debugging` | 调试 bug、找到根因 |
| React 技术栈 | `fw-react-best-practices` | 了解 React 最佳实践 |
| React 且涉及组件开发 | `fw-react-components` | 了解 React 组件规范 |
| 复杂类型问题 | `fw-typescript-advanced-types` | 处理 TypeScript 复杂类型 |
| 关键技能缺失 | `find-skills` | 查找缺失的技能 |

**⚠️ 注意**：
- 以上技能将在 Stage 5 实施研发时调用，本阶段仅做规划
- Stage 6 的验证技能（fw-accessibility、fw-web-design-guidelines）将在 Stage 6 根据实际改动类型判断调用

#### 3.6 生成过站产物
- 无论任务是否复杂，都需形成最小 Stage 2 过站产物
- 复杂任务再额外补充完整 `../templates/analysis/change-scope.md` 或 `../templates/analysis/capability-matrix.md`
- 只分析本任务实际需要的能力，不为临时任务额外沉淀长期文档

---

### 步骤 4：长任务判断

**范围分析完成后，判断是否是长任务**：

#### 判断标准

| 条件 | 是否长任务 |
| --- | --- |
| 预估修改文件数 > 5 | ✅ 长任务 |
| 涉及 3+ 个不同目录/模块 | ✅ 长任务 |
| 需要跨多个功能模块协调 | ✅ 长任务 |
| 预估需要多轮对话才能完成 | ✅ 长任务 |
| 单一文件修改、单一功能点 | ❌ 短任务 |
| 小范围 bug 修复 | ❌ 短任务 |
| 单一组件调整 | ❌ 短任务 |

#### 流程分支

- **是长任务** → 输出"接下来进入下一阶段：[执行计划]" → 进入 Stage 3
- **不是长任务** → 输出"接下来进入下一阶段：[资料补充]" → 直接进入 Stage 4（跳过 Stage 3）

---

### 步骤 5：输出分析结论并等待用户确认 ⚠️ 必须等待用户确认

**⚠️ 重要：范围分析完成后，必须等待用户确认才能进入下一阶段**

输出分析结论后，执行以下动作：

#### 5.1 更新状态文件为等待用户确认

使用 edit 工具更新该任务ID的状态块为：

```
**任务ID**: {当前任务ID}
**正在执行**: 范围分析
**阶段**: stage2
**状态**: waiting_user
**下一步**: 等待用户确认分析结论
**用户提出修改时**: 状态保持 stage2 → 执行合并更新 → 再次输出分析结论 → 等待确认
**循环路径**: stage2 → stage2 → 循环直到用户回复"继续"
```

#### 5.2 输出分析结论

根据长任务判断结果，输出对应的分析结论：

**长任务时**：
```
以上是本阶段的结论：[简要分析结论]。

【长任务判断】本次任务预估涉及多个文件/模块，属于长任务，需要建立执行计划。

请确认是否可以继续进入下一阶段：[执行计划]。
- 如有偏差或补充，请直接告诉我。
- 如无其他修改，回复"继续"即可。
```

**短任务时**：
```
以上是本阶段的结论：[简要分析结论]。

【长任务判断】本次任务预估范围较小，不属于长任务，将直接进入资料补充阶段。

请确认是否可以继续进入下一阶段：[资料补充]。
- 如有偏差或补充，请直接告诉我。
- 如无其他修改，回复"继续"即可。
```

#### 5.3 用户确认循环机制

- 用户回复"继续" → 进入下一阶段（根据长任务判断）
- 用户提出补充/修正/问题 → **理解并合并用户反馈** → 更新分析结论 → 再次输出等待确认
- **循环直到用户回复"继续"**
- 禁止：用户未明确回复"继续"就进入下一阶段

---

### 步骤 6：用户确认后更新状态文件（根据长任务判断）

**用户确认后，根据长任务判断结果更新状态文件**：

#### 长任务时

```
**任务ID**: {当前任务ID}
**正在执行**: 执行计划
**阶段**: stage3
**状态**: in_progress
**下一步**: 执行 stages/plan.md
**用户提出修改时**: 回到 stage2 → 状态保持 stage2 → 重新分析
**循环路径**: 无
```

#### 短任务时

```
**任务ID**: {当前任务ID}
**正在执行**: 资料补充
**阶段**: stage4
**状态**: in_progress
**下一步**: 执行 stages/supply.md
**用户提出修改时**: 回到 stage2 → 状态保持 stage2 → 重新分析
**循环路径**: 无
```

---

### 步骤 7：用户提出修改时的循环处理

**用户提出修改/问题时的循环路径**：

#### 7.1 状态保持 stage2

使用 edit 工具更新状态为：

```
**正在执行**: 范围分析
**阶段**: stage2
**状态**: in_progress
**下一步**: 合并用户反馈，更新分析结论
**用户提出修改时**: 状态保持 stage2 → 合并更新 → 再次输出分析结论
**循环路径**: stage2 → stage2 → 循环直到用户回复"继续"
```

#### 7.2 执行合并更新

- 读取用户反馈 → 合并到分析结论

#### 7.3 再次输出分析结论

- 输出更新后的范围分析结果

#### 7.4 再次进入等待状态

使用 edit 工具更新状态为：

```
**正在执行**: 范围分析
**阶段**: stage2
**状态**: waiting_user
**下一步**: 等待用户确认更新后的分析结论
**用户提出修改时**: 状态保持 stage2 → 合并更新 → 再次输出分析结论
**循环路径**: stage2 → stage2 → 循环直到用户回复"继续"
```

#### 7.5 循环直到用户回复"继续"

- 循环执行步骤 7.1 → 7.2 → 7.3 → 7.4 → 7.5
- 直到用户回复"继续"，才进入下一阶段

---

### 禁止事项

- 禁止不读取配置文件就猜测路径
- 禁止在等待用户时不更新状态为 waiting_user
- 禁止用户未明确回复"继续"就进入下一阶段
- 禁止输出模糊的"[执行计划]或[资料补充]"，必须根据判断输出明确的下一阶段名称
